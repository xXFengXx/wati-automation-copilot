# Automation Builder Copilot

**Problem and MVP.** A business user should be able to turn an automation idea into an understandable chatbot flow and test the paths before committing to it. This prototype provides English intent input, real DeepSeek generation, a Wati-style node graph and downloadable JSON, structural/risk review, a plain-English explanation, and an interactive conversation simulator. It supports nine node types across qualification, timed follow-up, and API failure scenarios. Graph editing, production delivery, authentication, and native Wati import are outside the MVP.

**Architecture and decisions.** React renders the flow and simulation. FastAPI owns a Pydantic flow contract, graph/data-flow validator, bounded in-memory stores, and deterministic interpreter. DeepSeek creates the artifact and explanation; it does not improvise execution. Explicit node semantics make failures reproducible. A conservative evidence check blocks destinations and timing without support in the prompt; it does not prove full business correctness. The graph and simulator use the same immutable flow. Business APIs, assignments, triggers, and virtual time are explicitly simulated. New questions/lookups invalidate old values, including on timeout or failure. Invalid flows remain inspectable but cannot execute.

**AI and agents.** Codex was used to clarify scope with the user, document domain language and an architectural decision, implement the stack, and design/run regression tests. A fact-finding sub-agent checked the assignment, official node reference, DeepSeek API contract, and local tools. DeepSeek is also a product capability: live generation and explanation, with clarification requests for missing essential business details. No runtime template fallback disguises an inference failure.

**Review and quality.** Fifty-six backend tests and seven browser tests passed, covering branching, timing, malformed URLs, overwritten variables, duplicate answers, provider errors, and resizing a graph. Real DeepSeek acceptance passed three generated scenarios and seven paths, plus clarification for a missing help URL and vague timing. Checks verified Sales/Support routing, the supplied URL, virtual time, and no successful result after API failure. A real-provider browser check also verified the graph, conversation, and desktop/mobile layout. Explanations were reviewed against execution semantics. This is a small sample, not a reliability guarantee. Final candidate human review and recording remain submission steps.

**Trade-offs and V2.** In-memory state and read-only wiring keep the take-home focused on the backend. Cycles are rejected; supported conditions, timing phrases, and flat API fixtures are intentionally limited. AI explanations and risk rules are not exhaustive guarantees. V2 would add richer semantic evaluation, versioned editable drafts, persistent sessions, authentication and rate limits, then an authorized business execution layer with endpoint restrictions and secret management. A 3–5 minute recording remains a submission step; hosting is optional.
