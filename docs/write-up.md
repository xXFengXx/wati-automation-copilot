# Automation Builder Copilot

**Problem and MVP.** A business user should be able to turn an automation idea into an understandable chatbot flow and test the paths before committing to it. This prototype provides English intent input, real DeepSeek generation, a Wati-style node graph and downloadable JSON, structural/risk review, a plain-English explanation, and an interactive conversation simulator. It supports nine node types across qualification, timed follow-up, and API failure scenarios. Graph editing, production delivery, authentication, and native Wati import are outside the MVP.

**Architecture and decisions.** React renders the flow and simulation. FastAPI owns a Pydantic flow contract, graph/data-flow validator, bounded in-memory stores, and deterministic interpreter. DeepSeek creates a structured artifact and explanation; it does not improvise execution. This makes branches and failures inspectable and reproducible, at the cost of limiting the supported node semantics. The graph and simulator consume the same immutable flow. Real inference is separated from explicitly simulated business APIs, assignments, triggers, and virtual time. Every API has success/error paths; question timeouts do not create an answer. Invalid flows remain inspectable but cannot execute.

**AI and agents.** Codex was used to clarify scope with the user, document domain language and an architectural decision, implement the stack, and design/run regression tests. A fact-finding sub-agent checked the assignment, official node reference, DeepSeek API contract, and local tools. DeepSeek is also a product capability: live generation and explanation, with clarification requests for missing essential business details. No runtime template fallback disguises an inference failure.

**Review and quality.** Forty backend tests and seven browser tests passed, covering routing, waits, failure paths, undefined data, duplicate answers, provider errors, and resizing an existing graph. Real DeepSeek acceptance also passed: three generated scenarios and seven paths, checking Sales/Support routing, the supplied help URL, virtual timing, and absence of success data after API failure. A separate real-provider browser check verified generation, graph, conversation, trace, and desktop/mobile layout. Generated explanations were checked against execution semantics. This is a small live sample, not a reliability guarantee. Candidate human review and the final recording remain their own submission steps; no human review is claimed on their behalf.

**Trade-offs and V2.** In-memory state and read-only wiring keep the take-home focused on the backend. Cycles are rejected; supported conditions and flat API fixtures are intentionally limited. AI explanations and risk rules are helpful, not exhaustive guarantees. V2 would add a curated live-model evaluation set, richer domain checks, versioned editable drafts, persistent sessions, authentication and rate limits, then a separately authorized business execution layer with endpoint restrictions and secret management. The final recording follows the supplied demo script; hosting is optional.
